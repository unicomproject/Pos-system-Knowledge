# Flow 4 — Create Tenant Wizard Field-to-Table Matrix

## Draft storage decision

Use a dedicated `platform_tenant_onboarding_drafts` table. Partial data must not be written into `tenants` because current final creation immediately builds subscription, entitlements, tenant admin, invitation and optional invoice rows. Mixing partial and production aggregates would weaken required constraints and trigger lifecycle side effects.

### New draft table

| Column | PostgreSQL type | Null | Rule/index |
|---|---|---:|---|
| `id` | uuid | No | PK |
| `owner_platform_user_id` | uuid | No | FK platform user; index with status/updated_at |
| `created_by_platform_user_id`, `updated_by_platform_user_id` | uuid | No | FK platform user; immutable creator, latest successful writer |
| `status` | varchar(24) | No | `in_progress`, `finalizing`, `completed`, `discarded`, `expired` check |
| `current_step` | smallint | No | 1–7 check |
| `completed_steps_mask` | smallint | No | server derived; 0–127 |
| `progress_percent` | smallint | No | server derived; 0–100 |
| `payload_json` | jsonb | No | versioned structured payload; default `{}` |
| `schema_version` | integer | No | draft payload migration contract |
| `tenant_code_normalized` | varchar(60) | Yes | advisory lookup index |
| `tenant_slug_normalized` | varchar(100) | Yes | advisory lookup index |
| `requested_domain_normalized` | varchar(253) | Yes | advisory lookup index |
| `admin_email_normalized` | varchar(320) | Yes | advisory lookup index |
| `version` | bigint | No | starts 1; atomic increment on successful update |
| `finalize_idempotency_key` | varchar(100) | Yes | accepted key for this locked draft; no globally unique key-only index |
| `finalize_request_hash` | char(64) | Yes | SHA-256 of canonical finalize input |
| `created_tenant_id` | uuid | Yes | FK tenant; set once completed |
| `last_error_code` | varchar(100) | Yes | safe diagnostic code only |
| `created_at`, `updated_at`, `expires_at` | timestamptz | No | UTC; expiry defaults from configurable retention |
| `discarded_at`, `completed_at` | timestamptz | Yes | terminal timestamps |

`UPDATE ... WHERE id = @id AND version = @expected` must increment `version`; zero rows means 409. Finalization locks the PK row and accepts exactly one `(draft id, key, request hash)` tuple. A repeated tuple returns `created_tenant_id`; a different key/hash after acceptance conflicts. Do not create a global unique index on the key alone. JSON schema versioning is mandatory because drafts can outlive a deployment.

### New onboarding operation table

Business purpose: retain post-commit payment/delivery progress and retry state without polluting `tenants.status`.

| Column | PostgreSQL type | Null/default | Constraint/index/audit |
|---|---|---|---|
| `id` | uuid | No / generated by application | PK |
| `draft_id` | uuid | No | Unique FK to draft, restrict delete |
| `tenant_id` | uuid | No | Unique FK to tenant, restrict delete |
| `provisioning_status` | varchar(32) | No / `SUCCEEDED` after atomic finalize | Check: `PROCESSING`, `SUCCEEDED`, `FAILED_RETRYABLE`, `FAILED_FINAL` |
| `payment_status` | varchar(24) | No / derived | Check: `NOT_REQUIRED`, `PENDING`, `CONFIRMED`, `FAILED`, `WAIVED` |
| `invitation_status` | varchar(24) | No / derived | Check: `NOT_ELIGIBLE`, `PENDING`, `SENT`, `FAILED`, `ACCEPTED`, `EXPIRED` |
| `last_error_code` | varchar(100) | Yes / null | Safe code only; never provider payload/PII |
| `retry_count` | integer | No / 0 | Check `>= 0` |

| `created_at`, `updated_at` | timestamptz | No / transaction UTC | `updated_at` concurrency token; index for status polling |

All status transitions and retry increments are audited with operation/tenant/draft correlation. There is one operation per completed draft and tenant.

### New tenant contact table

Business purpose: persist billing and support contacts without duplicating the primary tenant profile identity or overloading address rows.

| Column | PostgreSQL type | Null/default | Constraint/index/audit |
|---|---|---|---|
| `id` | uuid | No / application UUID | PK |
| `tenant_id` | uuid | No | FK tenant, restrict delete; tenant predicate mandatory |
| `contact_type` | varchar(20) | No | Check `BILLING` or `SUPPORT` |
| `contact_name` | varchar(200) | No | Trimmed, 2–200 |
| `email` | varchar(255) | Conditional / null | Required for `BILLING`; normalized lowercase comparison |
| `phone` | varchar(40) | Yes / null | E.164 where possible; support requires email or phone |
| `status` | varchar(20) | No / `ACTIVE` | Check `ACTIVE`, `INACTIVE` |
| `created_by_platform_user_id`, `updated_by_platform_user_id` | uuid | No | FK platform user, restrict delete |
| `created_at`, `updated_at` | timestamptz | No / transaction UTC | Audit/concurrency evidence |

Use partial unique index `uq_tenant_contacts_active_type (tenant_id, contact_type) WHERE status='ACTIVE'`; add check constraints for billing email and support reachability. Contact values are masked in audit output. No soft delete field is added; status is the lifecycle mechanism.

### Tenant-profile and entitlement additions

| Owner / column | Business purpose | Type/null/default | Validation/index/unique/audit |
|---|---|---|---|
| `tenant_profiles.registration_number` | Legal-registration reference and duplicate warning | varchar(100), nullable, null | Trim; non-unique expression index on `lower(btrim(registration_number))` where non-null; masked audit |
| `tenant_profiles.tax_number` | Tax/VAT reference and duplicate warning | varchar(100), nullable, null | Same non-unique normalized index; masked audit |
| `tenant_feature_entitlements.override_reason` | Explain a platform override | varchar(500), nullable, null | Required when new source type is `OVERRIDE`; no index; audit full reason subject to PII scrub |

Reuse existing entitlement `source_type`, `source_reference_id`, `effective_from` and `effective_until`; add `OVERRIDE` to the source-type vocabulary. `effective_until IS NULL` means an explicitly permanent override, so no duplicate permanent flag is added.

### New shared integration outbox table

No outbox entity/table exists in the inspected source. A shared table is justified because payment-link, email and activation delivery must be committed atomically and retried outside the transaction; Flow 4 must not create separate email/payment outboxes.

| Column | PostgreSQL type | Null/default | Constraint/index/audit |
|---|---|---|---|
| `id` | uuid | No / application UUID | PK |
| `event_type` | varchar(120) | No | Allow-listed application event code |
| `aggregate_type` | varchar(80) | No | `tenant_onboarding` for Flow 4 |
| `aggregate_id` | uuid | No | Operation ID; indexed with created time |
| `aggregate_sequence` | bigint | No | Atomic monotonic value; unique with aggregate type/ID to preserve created→activated ordering |
| `tenant_id` | uuid | Yes / null | FK tenant where applicable, restrict delete |
| `payload_json` | jsonb | No | Versioned minimum delivery payload; never raw token, password, card data or provider secret |
| `payload_schema_version` | integer | No / 1 | Check `> 0` |
| `idempotency_key` | varchar(180) | No | Globally namespaced event key; unique |
| `status` | varchar(24) | No / `PENDING` | Check `PENDING`, `PROCESSING`, `DELIVERED`, `FAILED_RETRYABLE`, `FAILED_FINAL` |
| `attempt_count` | integer | No / 0 | Check `>= 0` |

The worker claims rows with a bounded lease/`SKIP LOCKED`, increments attempts atomically and uses the event idempotency key at the provider adapter. Audit records state/result but not the outbox payload.

## Final field mapping

There is no current billing-account aggregate. R1 does not add a duplicate `billing_accounts` table: the tenant subscription owns billing cycle/status/terms, the active BILLING contact and address own invoice identity/location, invoices own charges, and payment link/transaction tables own collection. This composition satisfies the wizard and matches the existing billing architecture; a separate account would duplicate tenant/subscription ownership without an approved multi-account use case.

## Constraints and isolation

- Keep global unique constraints on normalized tenant code, slug and domain.
- Tenant-local tables require `tenant_id`, FK to `tenants`, composite/unique tenant-scoped keys, and explicit tenant predicate in repositories. The current database does not establish PostgreSQL row-level security; documentation must not claim RLS coverage.
- `tenant_users` is unique by `(tenant_id, email)`. Fix the current repository query that checks email across every tenant and ignores its normalized variable.
- Finalization catches `23505` unique violations and maps the named constraint to a field-level 409.
- Use a DB sequence, row lock or atomic increment for `tenant_subscription_history.sequence_number`; current `COUNT + 1` is race-prone.
- Current `tenants.updated_at` is an EF concurrency token for post-create mutation. Draft concurrency uses its own monotonic `version`.
- Deletes are restricted/cascaded deliberately: discarding a draft must never cascade to a completed tenant; completed draft/receipt is retained for audit/idempotent replay.

## Migration requirements

Create forward-only migrations in this order: `AddPlatformTenantOnboardingDraftsAndOperations`; `AddTenantOnboardingContactsAndProfileIdentifiers`; `AddSharedIntegrationOutbox`; `AddTenantEntitlementOverrideReasonAndSource`; `AlignTenantSubscriptionPlanAuthority` to remove the unconditional database `monthly` default while preserving existing populated rows. Exact timestamp prefixes are generated at implementation time. New tables need no data backfill. Profile identifier and override columns default null. Existing entitlements retain `MANUAL`; no historical row is recategorized. The billing-cycle default removal changes only future inserts; existing values remain. Each Down migration drops/reverses only objects introduced by its Up and is development rollback support, not a production rollback plan. Update the EF snapshot, run PostgreSQL model-shape/index/check/FK tests and verify the deployed schema. Do not edit `20260702182515_AddTenantCreateWizardSupport`, `20260707185919_UpdateTenantAuthAndFoundationEntities`, or lifecycle migrations.
